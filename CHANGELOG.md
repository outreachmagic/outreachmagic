# Changelog

## [Unreleased]

## [1.9.1] — 2026-09-17

### Fixed

- **A lead's status could roll back to an older one after a pull.** A pull applies the event stream first and workspace snapshots after it, and the snapshot apply overwrote the status without looking at its age — so a snapshot pushed yesterday (including our own, echoed back by the relay) replaced the positive reply that arrived overnight with the out-of-office before it. Status is now written by one function, `set_lead_status`, and the latest fact wins by **event time**: a new `workspace_leads.current_status_at` records when the current status happened, anything older is ignored, and snapshots carry it as `status_at`. Snapshots from before this release carry no time and may only fill a blank status. Late-delivered webhook events get the same protection.
- **Status labels were stored in two spellings** (`out_of_office` from webhooks, `out of office` from snapshots and imports), so the same status compared unequal and re-queued the row on every sync. Labels are stored snake_case; the dashboard displays them with spaces.
- **A manual status change could not be rebuilt from its event.** `update-stage` logged the stage as `lead_status_raw` and the label only in the display field; the sheet review sync logged nothing at all. Both now log a `status_label`.

### Added

- **`pipeline.py repair-lead-status [--workspace W] [--since 90d|all] [--apply] [--json]`** — replays each lead's status events in time order and rewrites the current status, its run start and `current_status_at` wherever they disagree. Dry run by default; changed rows are queued for the next push.

## [1.9.0] — 2026-09-04

### Fixed

- **`verify-bulk` silently stopped at 5000 addresses.** The `--limit` flag on `verification-candidates`, the `limit=` argument on the subprocess bridge and the `LIMIT ?` bind in the query all existed already — nothing joined them up, so the bridge's own default of 5000 was always what ran, whatever you asked for. `verify-bulk` now takes `--limit N`, **`--limit 0` removes the cap**, and candidate results carry `limit` and `truncated` so a capped set can never again be mistaken for a complete one. `--include-valid` and `--include-mv-attempted` are now on `verify-bulk` too; both were previously reachable only through the undocumented `--all`, which is exactly the two of them together. A bulk submit is billed per address, so `--dry-run` reports the cap alongside the credit count. (Reported as "`--max-age 0` also excludes valid rows" — it does not: `-0 days` resolves to `now`, and `email_verified_at < now` admits every past verification. The set looked short for the reason above. A test now guards that behaviour rather than a second code path being added for it.)
- **A meeting booked today did not appear on the Campaigns → Replies list.** The list dated a lead by when its *sentiment* started; the daily matrix counts meetings by *event date*. A lead that turned positive in July and booked a meeting today was therefore counted in today's meeting column and missing from today's list — while a lead that happened to turn positive the same day it booked did appear, which is why one day looked broken and the previous one did not. A meeting inside the window is now activity inside the window, with a new `meeting` kind (**Show → Meetings only**, `--kind meeting`) that outranks a plain reply, and an **In range because** column stating which fact put each row there. The card is now headed **Leads**: it stopped being a reply list when LinkedIn DMs joined it, and a booking made that plain.
- **Reassigning a sending domain's mailboxes to another workspace looked like it worked and then reverted.** Four separate causes: the dashboard treated an HTTP 200 carrying `{"status": "error"}` as success and printed "Saved." over a rejected write (this affected every form on the page); membership lives in `workspace_sender_accounts`, which the sync contract does not cover, so the change fired no outbox trigger, never reached the relay, and was reconciled away by the next pull from the relay's stale copy; the write matched `email_domain` with a bare `LOWER()` while the domains table groups on the stored value, so a padded or oddly-cased row was skipped; and the workspace checkboxes rendered unchecked on a form that submits the whole set, so the pane read as "add to X" while meaning "replace with X".
- **The `← Back` button never appeared on any slide-in pane.** The back-stack, the handler and the button were all wired; the panel's open function never refreshed the button's visibility, so the `display:none` left by the previous close survived every reopen. Back now works on the bounce, mailbox, sending-domain and blacklist panes.

### Added

- **One filter bar for the whole Campaigns tab.** Campaign was asked in three separate cards with three answers that did not have to agree, and the code had to say in prose that "the daily chart above is unfiltered". Campaign, kind, sentiment, lead status, tags and the two inclusion toggles are now asked once, at the top, and apply to the chart, the Leads list and the Campaigns table together; clicking a campaign row sets that filter rather than filtering one card. The state is the page's URL fragment, so a filtered view is a link you can send and a browser Back away. The daily chart now honours the tag filter as well (kind and sentiment do not apply to a per-day event matrix, and the chart's subtitle says so rather than ignoring them quietly). The positives anchor and the chart's count/rate axis stay with the view they affect: those choose a presentation, not a population.
- **`pipeline.py campaign-role` — mark a campaign as not-outreach.** The existing rule only classifies a campaign as a booking tool when *every* event on it came from one, so a genuine multi-event campaign that is nonetheless not outbound — a customer check-in sequence — correctly failed that test and had nowhere to be marked. `campaigns.reporting_role` records it: unset derives as before, `outbound` and `scheduling` force the two derived answers, and `excluded` keeps the campaign out of every chart, table, facet and rate. **Events still ingest and still show on the contact**; only the statistics change, and an excluded campaign's meetings are dropped rather than re-credited elsewhere. Reversible from the `⋯` button on any campaign row, visible again via **Include → excluded campaigns**, and available on `campaign-audit` / `campaign-replies` as `--include-excluded`.
- **Clicking a bounce failure filters the contacts beneath it.** A group row saying "6 contacts, 6 events" used to open a detail pane for one of the six, alongside three truncated sibling lists. It now narrows the contact table to exactly that group — the group's count and the filtered rows are the same set, asserted in tests — with a removable chip naming the filter. Every group key is clickable, not just the failure signature. The contact table drops Type and Code (identical on every row once you have filtered by a failure) for **Sending domain**, **Provider** and **Reseller**: the three facts that decide whether you pause one mailbox, one domain, or a reseller's whole batch. The detail pane keeps the verbatim message and what preceded it, adds the contact's recent history, and replaces its three sample lists with three buttons that filter the explorer to *all* related bounces. Same filters on the CLI: `deliverability bounces --signature / --recipient-domain / --smtp-code`.

## [1.8.0] — 2026-09-01

**One removal worth knowing before you upgrade:** `copy-insights`,
`segment-insights` and the Campaigns page's **Subject lines & copy** card are
gone. All three scored copy or segments off a lead's *current* status and the
first outbound email sent to them, which is not what made the copy work — and
status moves for reasons that have nothing to do with the message. Use
`campaign-audit` and the new `attribute-audit` for performance questions, and
`history` for message bodies.

### Fixed

- **The Best-performing lead attributes table ignored the date range.** It read three lifetime columns — `email_sent_count`, `total_replies_count`, `current_status_sentiment` — and took no date parameter at all, so the page's range control sat above an all-time answer. With a range it now recomputes every column from events inside it, using the same window helpers, the same definitions of a send and a reply, and the same tag and reply-kind filters as the Campaigns table. Positives are dated from `first_positive_at`. This is an **activity** window, stated on the card and in the payload: a lead contacted on day 13 who replies on day 16 is in the denominator and not the numerator — the same thing the Campaigns table has always meant by a date range.
- **Linking two replies as one conversation asked a three-state question through a two-state dialog.** OK meant one person was contacted first, Cancel meant the other — and also meant dismissing the box, so there was no way to say never mind and no way to tell the two apart. A wrong choice was then permanent: the reverse direction is a cycle and correctly refused, the refusal said only "would close a loop" with two bare ids, and the dashboard had no unlink route at all (the library and the CLI have had one all along). There is now a dialog with a named button per person, the existing link between the two shown *before* the choice with an **Unlink** button beside it, a refusal that names both people and the link to remove, and `POST /api/leads/unlink` behind it. "Already linked" no longer shares a success message with "linked".
- **The Campaigns tag filter offered every tag in the workspace**, most of them on leads no campaign in the window reached — so picking one emptied the table and read as a broken filter. It now offers the tags actually carried by leads those campaigns reached, with counts, from a dropdown rather than a type-ahead you had to already know the answer to use. Contacts keeps the type-ahead, where the list is long and you do know.
- **A timestamp `--until` was rounded up to the end of its day.** Right for a bare `--until 2026-08-14`, wrong for back-to-back windows computed from timestamps: each window overlapped the next by 24 hours and counted the same sends twice. A bare date stays inclusive of its whole day; a timestamp is now an exact bound.
- **`db-health`'s size and bloat hints described an action instead of naming one.** They now print the `pipeline.py archive` invocation to run.

- **The same person could exist twice with the same LinkedIn profile.** Not a normalization bug: `normalize_linkedin()` is correct and the canonical bare `linkedin.com/in/<slug>` was already the overwhelming majority (104,468 rows against 1,664 carrying `https://www.`). The cause was that `leads.linkedin_url` could be written **without a matching `lead_identities` row** — `resolve_lead` sets the column from the URL argument but takes identities from the caller's list, so the Prosp path (which passes email + Sales Navigator id) set the column and registered neither. Such a lead is unmatchable by LinkedIn forever, so the next import of the same person creates a second record. **193 leads were in that state, 166 of them from Prosp.** The evidence that this is the only duplicate mechanism: no two leads share a LinkedIn identity value — the unique constraint holds — so a duplicate can only exist where one side never registered. `resolve_lead` now appends the identity itself, in the one function that writes the column, so a call site written later cannot reintroduce the gap. `set_lead_linkedin_url` likewise stores the canonical form and registers the identity together.
- **`pipeline.py repair-linkedin`** normalizes stored URLs and backfills the missing identity rows, reporting first and writing under `--apply`. It also reports the duplicate pairs the backfill reveals rather than merging them — `leads.linkedin_url` is UNIQUE, which is exactly why the `www.` variants could coexist, so a colliding row is skipped and listed for `merge-leads` instead of failing the constraint. New `db_health` rule `linkedin_identity_gap` flags the state, which was previously invisible until it produced a visible duplicate.
- **LinkedIn DM replies never reached the Campaigns → Replies list.** The card is one row per lead keyed on `current_status_sentiment` / `current_sentiment_since`, so a lead with no sentiment could not appear whatever they actually did. Email sequencers ship a status label with every reply and that is what sets sentiment; Prosp ships none — **all 715 inbound LinkedIn events carried `lead_status_raw` NULL**, so 92 leads had a DM reply and only 12 showed up. The list now also includes leads whose most recent inbound reply carries no sentiment, anchored on that reply's time and rendered as `unclassified` rather than being assigned a verdict: defaulting inbound DMs to "positive" would corrupt every positive count on the Campaigns page. Sentiment still wins where it exists, so the list keeps reconciling with the daily sentiment columns.

### Added

- **`pipeline.py sql` cannot run forever.** SQLite has no statement timeout, so a join with no row-reducing predicate on `events` ran until someone killed the process — a real 4-way join on a multi-gigabyte database did exactly that. Queries are now cancelled after **10 seconds** (`--timeout N` to raise it, `--timeout 0` to remove the ceiling), through a progress handler, which needs no signals and leaves the connection usable.
- **`pipeline.py sql --explain`** prints the query plan and the shape warnings without running anything. The warnings also print (never block) on a normal run: `CROSS JOIN`, three or more joins with no `WHERE`, a large table with no date/campaign/lead predicate, `campaigns`/`workspace_leads` with no `workspace_id`, and `email_sent_count` in a query that also mentions campaigns. New `references/sql-pitfalls.md` documents each one with the shape that fixes it.
- **`campaign-audit --by-day`** attaches a per-day `sent` / `replies` / `bounces` / `meetings` array to every campaign row — the same window, scope and definitions as the totals beside it. It exists so the breakdown stops being hand-written SQL. **`--compare-previous-window`** returns the same-length window immediately before this one, per campaign and in total. Every response now echoes `since_resolved_utc` / `until_resolved_utc` / `window_days`.
- **`campaign-audit`'s daily volume as a sparkline** in each Campaigns row — drawn from the array the table already requests, so no extra query.
- **`pipeline.py attribute-audit`** — reply and positive rates by lead attribute (`industry`, `title`, `headcount`, `location_country`, `source`), with `--since`, `--kind`, and the same tag filters as `campaign-audit`. The dashboard's attributes card was the last big reporting surface with no CLI command, which is why the question kept being answered with hand-written SQL.
- **`pipeline.py tag list --since / --campaign-id`** returns the tags on leads those campaigns reached, rather than every tag in the workspace.
- **Column semantics where you are about to use the column.** `workspace_leads.email_sent_count` is a **lifetime, workspace-wide** counter, not sends in one campaign — reading it as the latter once reported 15,565 sends for a campaign that had sent 106. `current_sentiment_since` is when the status **last changed**, not first contact and not first positive, so windowing on it to find recent positives silently drops every lead whose status has not moved. Those and five more now carry a note that appears in `references/schema.md`, in `pipeline.py schema <table>` beside the column, and in the SQL lint. A test asserts every note still names a real column.
- **`v_campaign_lead_events`** — the per-campaign, per-lead shape `email_sent_count` looks like it provides and does not. Flat and unaggregated, so a caller's campaign and date predicates flatten into it.
- **Freshness next to the controls that set a window.** "Last pulled 40 minutes ago" in the page header is easy to scroll past, and a date-range answer read off stale data is wrong in a way its own numbers cannot show. `/api/sync/status` now carries the same freshness fields every CLI read command attaches.

- **Connects sent / accepted are in the daily-activity chart**, alongside emails and DMs — they are volume (the top of the LinkedIn funnel) rather than outcomes. A sixth palette token was added and the whole six-colour set re-validated for lightness, chroma, CVD separation and contrast in both light and dark; the dark steps are separately chosen, not a flip of the light ones.

### Performance

- **The Replies query keeps its old speed despite the wider selection.** The last-reply lookup is a CTE materialized once rather than a correlated subquery, the date filter is applied per branch on its own column instead of once over a `COALESCE` (which is not sargable and cost a 10x regression), and an indexed `event_type` pre-filter runs before the join to `events`. Measured on a 126k-event workspace: 0.4s before, 0.2–0.9s after.

### Removed

- **`copy-insights`, `segment-insights`, and the Campaigns page's Subject lines & copy card.** See the note above. Copy analysis worth having starts from the event stream and a real attribution window, not from `status = 'interested'`; that is its own change.

## [1.7.0] — 2026-08-10

**Two behaviour changes worth knowing before you compare a report to an older one:** the Campaigns page no longer counts booking-tool event types as campaigns and re-attributes their meetings to the campaign that earned them, so meetings and positives move between rows (and stop being double-counted); and the Contacts page is no longer scoped by the global date range.

### Fixed

- **Merging contacts from Campaigns froze the whole page.** `<dialog id="merge-contacts">` was parented inside `<section id="tab-contacts" hidden>`. Calling `showModal()` on a dialog in a `display:none` subtree renders nothing but *still* enters the modal state — the top layer engages and the rest of the document goes inert — so the page became unclickable with no dialog visible and only a reload cleared it. The same bug killed the company pane's merge button whenever Companies was the active tab. Shared dialogs now live outside every tab section, and `test_dashboard_html_hygiene` fails on any `<dialog>` inside a `#tab-*` section.
- **A large contacts export locked the dashboard until a reload.** A rejected POST (413/403) answered without reading its body, which desynchronizes a keep-alive connection: the unread bytes get parsed as the next request line, so every later request on that socket hangs, and the browser keeps the poisoned socket in its pool. Early returns now drain the body. The body cap is also raised per route (4 MiB on export/bulk/delete), because a "select all 8,000 matching" selection is ~64 KiB of ids on its own and `MAX_EXPLICIT_LEAD_IDS` (50,000) was unreachable through the shared cap.
- **Calendly slots were counted as campaigns, and one lead was counted twice.** `SCHEDULING_PLATFORMS` existed and was applied to exactly one query. Booking tools publish the booked event *type* ("30 Minute Meeting", "Popcam Rental Onboarding") with every webhook and ingest stores it as the campaign, so calendar slots appeared in the Campaigns table beside real sequences and the same lead landed in two rows. Scheduling campaigns are now excluded by default (a checkbox brings them back), and meetings are attributed through the same last-known-campaign chain the replies table uses — so a booking is credited to the outbound that earned it. A meeting that resolves to no campaign appears under one **Unattributed (scheduling)** row rather than vanishing.
- **A Calendly booking left the lead reading "interested" instead of "meeting booked".** Workspace routing is campaign-name based and nobody writes a routing rule per calendar slot, so the booking quarantined outright — the whole status-materialization block sits behind `if workspace_id:`. Scheduling events now fall back to the workspace the *lead* is already in. A lead in several workspaces stays quarantined with a reason naming the ambiguity, because guessing would mislabel a lead in the other.
- **Domains you never send from were listed as sending domains.** `log_event` bootstrapped a sender account from *any* event carrying a sender, inbound included — so a reply from `isenberg.umass.edu` made it one of your sending domains. 237 of 779 sender accounts in a live database had never sent anything. Accounts are now created only from outbound events (inbound still touches an existing one), the Deliverability page excludes never-sent domains by default, and `sender-domains prune-never-sent` clears what was already written (reports first; `--apply` to delete).
- **The Sync tab could not open a suppression row** — "Could not build payload: unknown entity_type: suppression". `suppression` was a first-class entity in `ENTITY_TYPES`, `OWNER_TABLES` and `SYNC_MAP`, but `_resolve_outbox_entity` had no branch for it. It has one now, and a new contract test asserts every member of `ENTITY_TYPES` resolves. Separately: the relay has no suppression endpoint, so those rows genuinely cannot drain — the panel now says so instead of letting a permanently-queued row read as a stuck push.
- **`import-profiles` blocked on a `company_conflicts` false positive.** Company-scoped personalization was bucketed by `company_id`, and every company that does not exist yet resolves to `NULL` — so a 1,551-row import of 1,000+ new companies reported one "conflict" holding 1,000+ distinct values and refused to run. Rows are now bucketed by the company they name (domain, else normalized name). Two rows disagreeing about the same new company are still a conflict; a thousand different companies never were.

### Added

- **The Campaigns table carries the daily-activity columns** — emails sent/received, DMs sent/received, connects sent/accepted, positive, negative, invalid, autoreply, meetings — built from the same SQL expressions as the matrix above it, so the two cannot drift. Status is gone: it described the campaign record, not its performance. Each lead is credited to its last known campaign only, so the columns sum to the workspace total instead of double-counting anyone in two campaigns.
- **Daily activity is two charts instead of one.** ~200 sends against ~5 positives on one linear axis left the outcome lines pinned to the baseline. The fix is *not* a second y-axis: where two scales line up is an arbitrary choice, so a dual axis invents a correlation that is not in the data. Volume and outcomes are now separate plots sharing an x-axis, plus a **% of sends** toggle that indexes everything to a common base. (`--series-4` / `--series-5` were referenced by the charts without existing, so a fourth series silently fell back to body ink; both are now defined and validated for lightness, chroma, CVD separation and contrast in light and dark.)
- **Two people, one conversation.** A contact replies, forwards us to a colleague, and both reply — one opportunity, two positives. `lead_links` records the relationship without destroying either record; reporting counts distinct conversation *roots*, so the whole thread counts once and is credited to the campaign that started it. Forwards may cross companies; chains of any length collapse to their origin; cycles and self-links are refused. **Link as one conversation** on the Replies list, `pipeline.py link-contacts add/remove/show/list` on the CLI. Wired as a first-class synced entity (outbox triggers, payload keyed by lead uids) — the relay endpoint is the one remaining piece, and the Sync panel says so.
- **Contacts gains "Last known campaign" and "Last reply"**, resolved by the same helper the Campaigns page uses rather than by reading `events.campaign_id` — the read that shows "—" for every bounce and auto-reply.
- **The contact pane shows where the record came from** — original and latest source, with detail and timestamps. All eight columns were stored and synced and nothing rendered them.
- **The company pane's contact list shows email, verification status and LinkedIn**, with the same click-to-copy cells as the Contacts table, so "can I actually reach anyone here" no longer needs a click per contact.
- **Bulk registration / blacklist checks.** Tick domains on the Deliverability page and check the selection; both CLI commands accept `--domains a.com,b.com`. Runs as a background job, because a DNSBL sweep over forty domains is minutes of DNS round trips.
- **The bounce pane answers three questions, not one.** "Other bounces in this campaign" implicates the copy; **other bounces from this sender** implicates one mailbox; **other bounces on this sending domain** implicates everything on it — which is the one that decides whether you pause a sender or the whole domain. Bounces can also be grouped by **recipient domain**.
- **Every slide-in pane has a name.** A stable id and a printed breadcrumb (`deliverability.bounce` → "Deliverability › Sender bounce detail"), documented in `references/dashboard-panes.md`, so a pane can be named rather than described. Back navigation now covers every cross-pane hop, not just lead ↔ company.
- **Dry runs answer the question they exist for.** `would_fill` names the columns each row would populate ("they had no LinkedIn before, will they after?"), computed by the same pure function the write path uses so the two cannot disagree. Real runs report `enriched_by_field` — email and LinkedIn fills were previously invisible in the summary because `filled` only came from `enrich_lead`.
- **Post-import duplicate report.** `duplicate_candidates` lists same-name/same-company groups the run touched. `--on-identity-conflict {review,merge,create}` decides what happens when a row's composite identity already belongs to another lead — the shape of one person listed twice under two LinkedIn URLs. Default `review`: create, but report both records. `merge` folds them; nothing merges silently, because two people can legitimately share a name, a title and an employer.
- **AI Ark import preset.** Raw exports import with no preprocessing, including `AI Ark People ID` → `external_id` so re-pulls dedupe on identity tier 1. Format-scoped aliases (`FORMAT_HEADER_ALIASES`) keep vendor spellings out of the global table.

### Changed

- **Contacts is no longer date-filtered.** It is a roster of every person in the workspace, not a report on a window. The list was range-scoped while its own export was not, so "export what's on screen" quietly shipped more rows than the screen showed.
- **Event history shows the subject and a "Show full message" toggle, with no preview snippet.** Twenty events meant twenty two-line excerpts — long enough to scroll past, never enough to read. A message with no stored body still shows its preview, because there it is the only text that exists.
- **The Deliverability Activity dropdown is gone**, replaced by one "Exclude never sent from" checkbox. The dropdown offered five windows of its own, unrelated to the page's date range, so the domain list and the numbers under it could describe different periods. The range at the top now decides the period.
- **Company sync payloads omit null fields** inside `domain_identities` and `public_emails`. Safe because those are whole-array replacements — an absent key and a null key mean the same thing to the reader. Deliberately *not* extended to fields the relay merges, where "absent" and "cleared" must stay distinguishable.

## [1.6.0] — 2026-08-07

### Fixed

- **DNSBL checks reported every domain as blacklisted when the lists were only rate-limiting us.** Spamhaus answers `127.255.255.x` and URIBL answers `127.0.0.1` to queries they refuse to serve — a real DNS answer meaning "not now", not "listed". The code special-cased Spamhaus's range and read URIBL's refusal as a listing, so on a rate-limited resolver a scan flagged *every* domain and stored that verdict. Response codes are now decoded per list (`blacklist_monitor.RESPONSE_CODES`); refusals and timeouts are retried with jittered backoff and, if they persist, recorded as `check_failed` — its own state, never "clean" and never "listed". Queries are also paced, since firing eight lookups per domain across a batch is what earns the rate limit. `newly_listed` only fires on a genuine clean→listed flip where the prior scan actually succeeded, so a refused query cannot page you. Deliberately **not** taken: falling back to a public resolver — Spamhaus and URIBL refuse public-resolver traffic by policy, so `@8.8.8.8` would make Spamhaus results worse. `dnsbl_resolver` in the config points checks at a local recursive resolver instead.
- **A partial blacklist scan erased the other tier's results.** `--tier tier1` overwrote the whole `dnsbl_status` record, so yesterday's tier-2 answers vanished and the domain read as never checked against them. Scans now merge by list name, each keeping its own `checked_at`, and carry `tiers_scanned` / `partial`.
- **`pull` crashed with `no such column: dedupe_hash` on any database created before 2026-07-13.** `relay_ingested` was changed to store a hash instead of the raw dedupe key and no migration ever shipped with it, so the scripts moved and the file did not. The table is now rebuilt in place (old keys hashed; an unhashable one is dropped, costing one idempotent re-ingest). Any remaining schema-behind error is caught at the CLI entry point and reported as an instruction rather than a raw SQLite message.
- **The "Provider" column on Sending domains showed the reseller.** It was literally filled from `reseller`, so a domain bought through a reseller reported that reseller as the platform sending its mail. `sender_domains` now has its own `provider` column and the table shows both.
- **Contacts "Tags" column showed `undefined`** — `dashboard.html` declared `function renderTagChips` twice at top level: the table-cell renderer that takes a row, and the tag-filter-bar renderer that takes nothing. Hoisting means the second wins for the whole script, so both tables using the Tags column called the filter-bar renderer, printed its `undefined` return into every row, and re-rendered the filter bar once per row as a side effect. The filter-bar one is now `renderTagFilterBar()`. New `tests/test_dashboard_html_hygiene.py` fails on any duplicate top-level `function` declaration — there is no bundler in front of this file, so this class of bug ships silently.
- **Lead panel's "Existing tag…" dropdown was always empty** — it fetched `/api/tags` with `api()`, which does not append `?workspace=`; the route is workspace-scoped and rejects the request, and a `.catch(() => {})` swallowed it. Now uses `get()`. The hygiene test also fails on any `api()` call to a workspace-scoped route.
- **Dashboard pull finished successfully and then reported "[Errno 32] Broken pipe"** — the pull worker redirected stdout into the console log but left stderr alone, and `pipeline_sync._relay_log` wrote to stderr with a bare `print`. Under a harness that closes stderr the first diagnostic raised `BrokenPipeError`, which `SyncManager._run` catches as `OSError` and files as a failed run — after the log had recorded a complete successful pull. `_relay_log` now goes through `progress.warn` (already `BrokenPipeError`-safe, and whose docstring describes this exact failure), and the pull worker redirects stderr too.
- **Export said "Exporting…" and then nothing, taking the database and the app with it** — `full` is ~30 correlated subqueries per row, and `export_to_csv` materialized the entire result set (message bodies included) into a list of dicts before writing a byte, inline on the request thread with no timeout and a toast that expired after 2.8s. Rows now stream from the cursor straight into the writer, and the dashboard export runs as a background job through `SyncManager` — the same single-flight lock, status endpoint and console drawer that pull and push use, with per-2,000-row progress and the file path in the completion line. The CLI stays synchronous.
- **`import-profiles` renamed people** — a sheet of `lead_id` + personalized columns has no name column, so `personalized_first_name` was promoted into `leads.name`: "Brian Williams" → "Brian". Promotion no longer happens when the row identifies an existing lead, and `--mode personalization-only` makes it structurally impossible for a whole file.
- **`import-profiles --record-type` was documented but did not exist** — `SKILL.md` told you to pass it and argparse rejected it. `import_profiles()` had accepted the parameter all along; only the CLI flag was missing.

### Fixed

- **Dashboard: switching workspace now actually refreshes the page.** The fetch was always correct — the failure was downstream, in three places at once. Every loader is `const d = await get(…); if (!d) return;`, so on an error, an empty response, or a slow one it returned *without touching the DOM*, leaving the previous workspace's rows on screen looking like current data; loaders now blank their containers **before** awaiting, so a table either repopulates or goes visibly empty. Per-workspace filter state survived the switch in the DOM — `contacts-campaign`, `contacts-tag`, `contacts-sender`, `daily-campaign`, `attr-campaign` still held ids belonging to the old workspace, so the requery legitimately returned nothing, which reads exactly like a broken switch; `resetWorkspaceScopedState()` clears them along with every cached payload and filter set. And two concurrent requests could resolve out of order, letting the workspace you just left win: `state.wsGeneration` is captured by `get()` at request time and a response arriving under an older generation is discarded (as a `null`, not a rejection — a workspace switch is not an error and should not raise a toast).
- **Dashboard: workspace sending domains** now derive from the workspace's own mailboxes (LEFT JOIN to `sender_domains` for reseller/pricing/DNSBL) — workspaces whose domains were never registered in `sender_domains` (e.g. newer client workspaces) previously showed an empty domain list.
- **Agent-originated stage changes are now indexed into `workspace_lead_events`** (like relay-ingested status events already were), so they show up in workspace-scoped analytics and CRM activity windows. Previously `update-stage` wrote the status event to `events` only.
- **Mailbox bounce-rate `-1` sentinels** (provider "not measured") no longer render as -100%.
- **`sync --status` no longer derives lead/workspace pending counts from the deprecated `updated_at` cursor.** A fully-pushed lead whose `updated_at` happened to be newer than an earlier `last_sync` value was reported pending forever, even with an empty outbox — the classic false "half my data never synced" reading. `get_sync_status()` now reads `leads_pending`/`workspace_leads_pending` from the outbox, same as the already-correct `get_local_pending_counts()`.
- **Locally-deleted leads, workspace memberships, and companies now actually tell the relay.** Previously, only merges pushed a delete (via the separate `lead_merges`/`company_merges` path) — any other delete (a direct delete, a workspace removal) left an unconsumed `outbox` tombstone and a permanent ghost row on the relay. `lead_workspace` deletes (removing a lead from a workspace) had **no push path at all** — every workspace removal orphaned a `relay_lead_workspace_snapshots` row forever. `sync` now drains these tombstones and pushes real `lead_core_delete`/`lead_workspace_delete`/`company_core_delete` entries (the relay already had working handlers for all three; this was a pure client-side gap). Also fixes a wire-format bug found while building this: the delete trigger captures the bare `uid` column, not the `uid:`-prefixed form the relay actually stores as `entity_key` — sending the raw form would have matched zero rows and silently done nothing.

### Fixed

- **`BrokenPipeError` in background batch runs** — progress output now silently drops when the parent agent disconnects stdout/stderr rather than crashing the process.
- **Concurrent batch process SIGTERM** — `batch-find` now acquires an exclusive `flock()` lock at startup. A second concurrent batch from another agent session fails immediately with a clear message instead of blocking and getting killed by the host watchdog.
- **`--skip-catchall-after` pre-flight seeding** — at batch start, domains already confirmed catch-all in `lead_provider_observations` are seeded into the in-memory skip table so the first lead from a known-bad domain is skipped without an API call, not just leads discovered mid-run.
